# Infrastructure (Terraform)

Creates Sitewatch's server on AWS and everything it needs to send email, plus the DNS records and the Pages project on Cloudflare. The application itself is deployed by CI (see the main [README](../../README.md)).

## What it creates
| Resource | What it is for |
|---|---|
| Own VPC, public subnet and gateway | Isolated from any other project in the account |
| EC2 `t3.micro`, Ubuntu 24.04, encrypted 20 GB gp3 disk | Server for the API and PostgreSQL |
| Elastic IP | Fixed IP that `monitor-api.sergiomarin.dev` points to. A new one, or one you already own with `existing_eip_allocation_id` |
| Security group | **80/443 only from Cloudflare's ranges** (downloaded from cloudflare.com), **SSH only from your IP** |
| cloud-init | 2 GB swap, Docker and Compose, log rotation and secrets read from SSM |
| Instance role | Can only read its own SSM parameters and write PostgreSQL dumps to S3; allows Session Manager as an alternative to SSH |
| S3 buckets | One for nightly PostgreSQL dumps and one for the Terraform state: private, encrypted and versioned |
| SES: domain `monitor.sergiomarin.dev` | Verified with DKIM and its own MAIL FROM domain (`mail.monitor…`) so SPF aligns |
| SMTP IAM user | Can only send from `alerts@monitor.sergiomarin.dev` |
| SSM Parameter Store (SecureString) | `JWT_SECRET`, `DB_PASSWORD` and SMTP credentials, generated by Terraform |
| Cloudflare: `monitor-api…` | Proxied A record to the Elastic IP |
| Cloudflare: SES records | 3 DKIM CNAMEs, MX and TXT (SPF) of the MAIL FROM domain, and DMARC |
| Cloudflare Pages | Project `sitewatch` (direct upload from CI), domain `monitor.sergiomarin.dev` and its CNAME |
| Cloudflare: origin certificate | 15-year ECDSA certificate for `monitor-api…`, generated by Terraform and stored in SSM (`/sitewatch/tls/`). Only Cloudflare trusts it |
| Cloudflare: configuration rule | TLS "Full (strict)" **only** for `monitor-api…`; the zone's mode does not change |
| GitHub OIDC and role `sitewatch-github-deploy` | CI deploys without AWS keys: it can only run commands on this instance and only from `main` |
| AWS Budgets | Warning at 80 % of actual spend and 100 % of forecast, filtered by the `Project=sitewatch` tag |

## Decisions
- **`cpu_credits = "standard"`:** t3 instances default to *unlimited*, which bills CPU bursts separately. In *standard* the instance is throttled instead of raising the bill.
- **IMDSv2 required with a single hop:** containers cannot ask for the instance's credentials.
- **Secrets in SSM, never in the repo or in an image.** The parameter name is the environment variable's (`/sitewatch/env/JWT_SECRET`). `TELEGRAM_BOT_TOKEN` and the Grafana token are not managed by Terraform, so they do not end up in the state.
- **The state contains secrets** (generated passwords and the SMTP key). It lives in a private, encrypted, versioned S3 bucket (see below) and is never committed; `*.tfstate` and `backend.hcl` are in `.gitignore`.
- **Reusing an existing Elastic IP** (`existing_eip_allocation_id`): Terraform only associates it with the instance, with `allow_reassociation`, and does not manage it. It is taken from whichever instance had it, and `terraform destroy` does not release it: it stays yours and unassociated (it keeps billing until you associate or release it).
- **Cloudflare's ranges are read at `plan` time.** If Cloudflare changes them, the next `plan` shows the difference.

## Cloudflare
**The API name has a single level** (`monitor-api.sergiomarin.dev`, not `api.monitor.…`): Cloudflare's free certificate (Universal SSL) covers `domain` and `*.domain`, but not second-level subdomains, and with a deeper name every TLS handshake fails at the edge.

It only **adds** records and a project: whatever else the zone has (the website, email, Resend) is not managed here and is never touched. The API token goes in the `CLOUDFLARE_API_TOKEN` variable, never in the repo or in `terraform.tfvars`:

```bash
set -a; . ~/.config/sitewatch/cloudflare.env; set +a   # mode-600 file with CLOUDFLARE_API_TOKEN=...
```
Token permissions: zone `sergiomarin.dev` with DNS (edit), Zone (read), Zone Settings (edit) and Configuration Rules (edit); SSL and Certificates (edit) to create origin certificates; account with Cloudflare Pages (edit). The zone and account ids go in `terraform.tfvars`.

TLS "Full (strict)" and the origin certificate apply **only** to `monitor-api` (a configuration rule), without changing the mode of the whole zone, which your website also uses.

## GitHub OIDC: the repository name in the token
New repositories use the *immutable subject*: the token carries not `repo:owner/name` but `repo:owner@<id>/name@<id>`, with the numeric ids, so nobody can impersonate the repository if it is renamed or deleted. The role's trust policy must use that same format or AWS rejects the role with "Not authorized to perform sts:AssumeRoleWithWebIdentity". Read it with `gh api repos/OWNER/REPO/actions/oidc/customization/sub` and put it in `github_oidc_subject_prefix` in `terraform.tfvars` (it does not need to go in the repository).

## Usage
```bash
cd infra/terraform
cp terraform.tfvars.example terraform.tfvars   # your IP with /32 and your email
cp backend.hcl.example backend.hcl             # the state bucket (see below)
terraform init -backend-config=backend.hcl
terraform plan -out=plan.tfplan                # review what will be created
terraform apply plan.tfplan                    # only after reviewing the plan
```
After applying:
1. **Confirm the SES email.** AWS sends a verification link to `alert_email`. Without it, the account (in the *sandbox*) cannot send you alerts.
2. **Create the DNS records** from `terraform output ses_dns_records` (3 DKIM CNAMEs, MX and TXT of the MAIL FROM domain, and DMARC). Until then SES does not verify the domain. The Cloudflare module automates this.
3. **Telegram token** (optional): `aws ssm put-parameter --name /sitewatch/env/TELEGRAM_BOT_TOKEN --type SecureString --value '<token>'`, then redeploy.
4. **Check the boot:** `ssh ubuntu@<ip>` and `cat /var/lib/sitewatch/bootstrap-done`. The log is in `/var/log/cloud-init-output.log`. If your IP changed: `aws ssm start-session --target <instance_id>`.

**Optional budget (`enable_budget`):** the cost tag takes ~24 h to exist. Leave `enable_budget = false` on the first `apply` and set it to `true` afterwards; the budget is not created until then.

**First `apply` in an account without the cost tag activated:** the `Project` tag only shows up in Billing about 24 h after tagged resources are created, and until then `aws_ce_cost_allocation_tag` fails with "Tag keys not found: Project" (and the budget, which depends on it, is not created). That is expected: everything else is created, and repeating `terraform apply` after that time is enough.

`terraform destroy` removes everything except the Elastic IP when it was reused. SES identities and the budget can be recreated without problems.

## SES and the sandbox
A new account can only send to verified addresses and 200 emails a day. That is enough for your own alerts. Sitewatch **stays in the sandbox on purpose**: it is a portfolio demo, and the sandbox means the server cannot be used to email third parties. The application still verifies the email at sign-up (an address that is not confirmed never receives alerts), so asking AWS for production access later would be safe; until then the confirmation email only reaches addresses verified in SES.

## Backups and Terraform state

- **State**: lives in the `sitewatch-tfstate-<account>` bucket (encrypted, versioned, locked with a lock file). Copy
  `backend.hcl.example` to `backend.hcl` with that bucket name and run `terraform init -backend-config=backend.hcl`.
  The bucket is created by this same configuration, so the very first `apply` runs with a local state and the state
  is then moved with `terraform init -migrate-state -backend-config=backend.hcl`.
- **Database**: a systemd timer (`sitewatch-backup.timer`, 03:00 UTC) runs `deploy/backup.sh`, which streams
  `pg_dump` to `s3://sitewatch-backups-<account>/postgres/`. Dumps are kept 30 days. The instance role can only add
  objects there, so a compromised server cannot read or delete past backups.
- **Restore** (from a machine with admin access; try it on a scratch database first):
  ```bash
  aws s3 ls s3://sitewatch-backups-<account>/postgres/
  aws s3 cp s3://sitewatch-backups-<account>/postgres/<file>.dump .
  docker exec -i sitewatch-db-1 pg_restore -U sitewatch -d sitewatch --clean --if-exists --no-owner < <file>.dump
  ```
  A restore into an empty PostgreSQL 17 was verified on 2026-11-25 (users, sites, checks and Flyway history intact).
